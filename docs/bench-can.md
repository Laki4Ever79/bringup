# Bench test: a CAN link between two boards

What it proves: two Bringup boards joined by a CAN link exchange the link's messages on a real bus. Each message is one
Cyphal/CAN v1.0 single-frame message transfer (`include/linkcyphal.h`): its 29-bit identifier carries the message's
subject-ID and the sender's node-ID, and its data is the fields, packed little-endian as DSDL serializes them, then the
tail byte (`include/link.h`, generated by `src/codegen/firmware.ts`). The firmware build writes each message's
definition to `dsdl/bringup/<Name>.1.0.dsdl`, so `yakut` or `pycyphal` on a USB-CAN adapter can read the bus too. The ESP32-C3 sends it through TWAI and an STM32 (F103, F446)
through bxCAN.

Nothing here assumes what is on your bench: check the list below against what you have before starting.

## What it needs

| Item | How many | Notes |
|---|---|---|
| Two boards designed with the CAN link | 2 | Each carries an SN65HVD230DR transceiver (LCSC C12084), placed by the generator, and the link's JST SH 4-pin connector (CANH on IO1, CANL on IO2). |
| 120 Ω across CANH and CANL at each end of the bus | 2 | The board the link marks as a bus end has it already (`can.terminate`). Otherwise use a through-hole 120 Ω resistor at the far end of the cable. |
| A cable between the two connectors | 1 | A JST SH 4-pin cable, the pair twisted for anything longer than a few tens of cm. Its length must be within the spec's limit for the bit rate (`CAN_BUS_MAX_M`, src/system/spec.ts). |
| A USB cable per board | 2 | To flash each board and read its console. |
| A multimeter | 1 | Optional, for the termination check below. |

Boards without a transceiver of their own (a dev board or a breakout) need an SN65HVD230 module each, 3.3 V. A 5 V-only
transceiver (TJA1050, MCP2551) on a 3.3 V MCU needs a level check first, so don't use one unchecked.

## Steps

1. With both boards powered off and the cable connected, measure the resistance between CANH and CANL: about 60 Ω (two
   120 Ω terminators in parallel) is right. About 120 Ω means one terminator is missing; open circuit means none.
2. Flash both boards with the link test (`LINK_TEST`): `.venv/bin/pio run -d <firmware dir> -e <env>_linktest -t upload`.
   The env is `esp32c3_linktest` on the ESP32-C3 and `<profile>_linktest` on an STM32 (src/mcu/firmware.ts envFor).
3. Open both consoles at 115200 baud and reset both boards.
4. The sending board prints `LINK L1 sent reading` every half second. The receiving board prints
   `LINK L1 reading from <sender>: tempCx100=… rhx100=…` (the fields of the link's message).
5. Disconnect the cable. The sender prints `LINK L1: no CAN frame sent (…)` (ESP32: bus off or no acknowledge; STM32: no
   free mailbox or bus off). Reconnect it, and after the controller's automatic bus-off recovery the readings return.

## What a failure means

| You see | Likely cause |
|---|---|
| `the CAN controller didn't start` | The controller didn't initialise: the pins, the clock, or (STM32) a profile without `HAL_CAN_MODULE_ENABLED`. |
| `no CAN bit timing for this bus clock` (STM32) | No 8–25 time-quanta split divides the bus clock at this bit rate. Choose another bit rate. |
| Frames sent, nothing received | Termination (step 1), CANH/CANL swapped, or the two boards at different bit rates. |
| `a frame with an unknown definition (hash …)` | The two boards were built from different link definitions. Rebuild both from the same system spec. |
| `LINK CAN: subject … from node … is not one of ours, dropped` | A frame whose subject-ID this board doesn't know: the boards were built from different link definitions, or another Cyphal node shares the bus. Rebuild both from the same system spec. |

## What is proven without hardware, and what isn't

- **Proven:** both sides compile for the ESP32-C3 (TWAI) and the STM32F103 (bxCAN), in test/linktest-can.int.test.ts.
- **Proven, as an approximation:** two STM32 nodes exchange the frames on Renode's virtual CAN bus. Renode 1.17 has no
  CAN on the F103 and no F446 platform, so its F407 platform stands in: it has the same bxCAN at the same addresses.
- **Not proven without hardware:** the ESP32-C3's TWAI (QEMU models none) and the F103's bxCAN (Renode models none).
  That gap is why this bench test exists.
